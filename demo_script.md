# MediBridge — Faculty Demo Script

**Duration:** 3–5 minutes  
**Goal:** Demonstrate the complete patient registration → FHIR conversion workflow.

---

## Before the Demo

Ensure all three are running:
- ✅ Docker PostgreSQL: `docker compose up -d` (from the project root)
- ✅ Backend: `python -m uvicorn main:app --port 8000 --reload` (from `backend\`)
- ✅ Frontend: `npm run dev` (from `frontend\`)
- ✅ Seed data loaded: `python seed.py` (from `backend\`)

Open these tabs in advance:
1. http://localhost:5173 — MediBridge UI
2. http://localhost:8000/docs — Swagger UI

---

## Step 1 — Dashboard Overview (30 sec)

> *"This is the MediBridge dashboard. It shows real-time statistics pulled from PostgreSQL."*

- Show the **4 stat cards**: Total Patients, Successfully Converted, Pending, Failed
- Point to the **Recent Activity table** with sync status per patient
- Click **↻ Refresh** to show the data is live

---

## Step 2 — Register a New Patient (60 sec)

> *"Let me register a brand new patient during this demo."*

- Click **Patients** in the sidebar
- Click **+ Register Patient**
- Fill in:
  - Full Name: `Priya Venkat Nair`
  - Date of Birth: `2000-07-15`
  - Gender: `Female`
  - Phone: `+91-98000-12345`
  - City: `Chennai`
  - State: `Tamil Nadu`
- Click **Register Patient**
- ✅ See green success toast: *"Patient registered successfully! Change log entry created."*

> *"The patient is now saved in PostgreSQL. A database trigger has automatically written a CREATE event to the change_log table."*

---

## Step 3 — Sync Monitor: See the Trigger in Action (30 sec)

> *"This is the Sync Monitor — it reads directly from the change_log table, which PostgreSQL triggers populate automatically."*

- Click **Sync Monitor** in the sidebar
- Click **↻ Refresh**
- Show the new **CREATE** event for the newly registered patient
- Point out: **Status = pending → done** (may already be done after ~3 seconds)
- Show the **Operation** (CREATE), **Timestamp**, and **Validation** (valid)

> *"The background worker picks up pending events every 3 seconds using SELECT FOR UPDATE SKIP LOCKED to prevent duplicate processing."*

---

## Step 4 — FHIR Explorer: View the Generated Resource (60 sec)

> *"This is the FHIR Explorer — the core feature of MediBridge. It shows the SQL record on the left and the generated HL7 FHIR R4 Patient resource on the right."*

- Click **FHIR Explorer** in the sidebar
- Select `Priya Venkat Nair` from the dropdown
- Show the **left panel** (SQL fields) vs **right panel** (FHIR R4 JSON)
- Point out:
  - `resourceType: "Patient"`
  - Correct name splitting: `family: "Nair"`, `given: ["Priya", "Venkat"]`
  - Valid `gender`, `birthDate`, `telecom`, `address`
  - Validation badge: ✓ Valid (fhir.resources R4)
- Click **📋 Copy JSON** to copy the resource

---

## Step 5 — Update a Patient → FHIR Regenerates (60 sec)

> *"Now I'll update a patient's phone number and show that the FHIR resource regenerates."*

- Click **Patients** in the sidebar
- Find `Priya Venkat Nair` → click **Edit**
- Change Phone to: `+91-99999-00000`
- Click **Update Patient**
- ✅ See success toast: *"Patient updated. FHIR resource will regenerate."*
- Click **Sync Monitor** → Refresh → show new **UPDATE** event
- Click **FHIR Explorer** → select the patient → click **↻ Refresh**
- Show the updated phone number in the FHIR JSON

---

## Step 6 — API via Swagger UI (30 sec)

> *"MediBridge also exposes a proper REST API. Here's the Swagger UI auto-generated by FastAPI."*

- Switch to http://localhost:8000/docs
- Expand **GET /fhir/Patient/{patient_id}**
- Click **Try it out** → enter the patient ID (e.g., `P-1001`)
- Click **Execute**
- Show the FHIR R4 JSON response with proper `application/fhir+json` content type

---

## Step 7 — Dashboard Final Check (15 sec)

- Switch back to http://localhost:5173
- Click **Dashboard** → **↻ Refresh**
- Show updated counts (Total Patients now includes the new patient)

---

## Key Points to Mention

| Claim | Evidence |
|-------|----------|
| PostgreSQL triggers detect changes | Sync Monitor shows events written immediately after create/update |
| Background worker processes events | Status transitions: pending → processing → done |
| FHIR R4 compliance | Proper `resourceType`, `identifier`, `name`, `gender`, `birthDate`, `telecom`, `address` |
| Real validation | fhir.resources R4 library validates structural compliance (not HAPI — requires Java) |
| Updates regenerate FHIR | Update patient → new FHIR resource reflects change |
| Real backend data | All counts and records come from PostgreSQL — nothing is hardcoded |
